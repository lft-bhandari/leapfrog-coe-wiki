# LLM-Guided Graph Traversal for Wiki Navigation

**Status:** Research — not yet adopted  
**Date:** 2026-09-17  
**Related ADR:** [ADR-0001 — Wiki navigation over vector embeddings](../adr/0001-wiki-navigation-over-embeddings.md)

---

## Problem

The current `_load_wiki_context` function (`apps/api/app/services/chat_service.py:54`) answers queries with a keyword-overlap scan: it strips stop-words from the question, scores every `.md` file by how many keywords appear in it, and loads the top-6 by score. This has three structural weaknesses:

1. **No structure awareness.** Keyword frequency in raw text treats every page as an unordered bag of words. The wiki's typed graph (domain → concept → source, with `[[wikilinks]]` as edges) is ignored.
2. **Hallucinated relevance.** A source page that mentions the keyword in passing ranks the same as a concept page that defines it. The synthesized concept pages—the highest-quality context—are not preferentially surfaced.
3. **No progressive disclosure.** All pages are read flat. The reference implementation's three-layer ladder (index → page → raw) means most questions are answered from ~1 KB of curated prose; the current implementation loads up to 6 full pages every time.

## Reference Implementation: `llm-wiki-workshop` Layer 03

Source: `https://github.com/decodingai-magazine/llm-wiki-workshop/tree/main/03-llm-wiki-interactive/.agents/skills/03-llm-wiki-interactive`

The reference is an _agent skill_, not a Python library — it defines a protocol for a Claude Code agent to follow. The query path lives in `QUERY.md` and is described as steps Q.1–Q.8.

### The three-layer disclosure ladder (CONVENTIONS.md §2)

```
Layer 1: wiki/index.md → wiki/<subdir>/index.md   (one-line bullets per page)
Layer 2: The wiki page itself (source / entity / concept)
Layer 3: raw/   (verbatim source — almost never needed)
```

The agent **stops as soon as the question is answered**. Most answers close at layer 2. Layer 3 is reachable but discouraged ("A wiki that forces every reader back into raw/ has failed at its job").

### Query path (QUERY.md Q.2–Q.5)

```
Q.2  Load wiki/index.md + the one or two subdir index files that look relevant.
Q.3  Walk the disclosure ladder — prefer entity/concept pages over source pages.
Q.4  Classify: repo-scoped or general.
Q.5  Answer from the pages read.  
     Always write a slim question page.  
     Write a note only if the answer cited ≥2 wiki pages.
```

**Key insight:** the LLM reads only index files first, decides _which_ pages to fetch next, fetches those, and decides whether to stop or go deeper. There is no batch load. The graph traversal is deterministic (only wikilink edges are followed); the LLM only decides _which edge_ to take at each step.

### Write-back on query (QUERY.md Q.5, Q.7, Q.8)

The reference adds to the wiki as a side-effect of answering:
- A slim `wiki/questions/YYYY-MM-DD-<slug>.md` page is always written.
- A `wiki/notes/<slug>.md` is written if the answer used ≥2 pages.
- Unanswerable questions are appended to `wiki/open-questions.md`.

This write-back is out of scope for the immediate navigation fix but is the designed end state of layer 03.

### Ingestion structure that enables traversal (CONVENTIONS.md §3, PAGES.md)

Every source page declares its entities and concepts in frontmatter:

```yaml
entities:
  - "[[wiki/entities/claude-code]]"
concepts:
  - "[[wiki/concepts/mcp]]"
```

`scripts/count_mentions.py` counts how many source pages declare each slug. Only slugs with ≥2 mentions get a dedicated concept/entity page. The index files are regenerated by `scripts/build_index_md.py` from frontmatter — they are the navigable map the LLM reads first.

## Our Wiki Structure — What We Have

Our wiki layout (`wiki/`) diverges from the reference in two ways:

| Dimension | Reference | Ours |
|---|---|---|
| Top-level grouping | `sources/`, `entities/`, `concepts/`, `questions/`, `notes/` | `sources/`, `domains/<name>/` |
| Index format | Auto-generated from frontmatter (`build_index_md.py`) | Hand-written: `wiki/index.md` lists `[[domains/general/index]]`; domain index lists source slugs as plain wikilinks |
| Frontmatter links | `entities:` + `concepts:` lists on every source page | `domain:` field only; no `entities:`/`concepts:` lists |
| Concept/entity pages | First-class, ≥2 threshold | Concepts live inside domains; no distinct concept pages |

Our `synthesize.py` (`scripts/core/synthesize.py:24–43`) writes source pages with a `domain:` field and instructs the LLM to use `[[wikilinks]]` in prose, but does not emit the structured `entities:` / `concepts:` frontmatter arrays. The `wiki_graph.py` (`scripts/core/wiki_graph.py:9–25`) extracts bare wikilinks from prose (`[[term]]` with no `/`), which are the graph edges, but they are not reflected back into frontmatter.

**What we have that supports traversal:**
- `WikiRepository.root_index_exists()` / `write_root_index()` — the index exists (`wiki/index.md`).
- `list_slugs(page_type)` — can enumerate sources, concepts, etc.
- Wikilinks in source prose — graph edges exist, just not in frontmatter.
- Domain subdir indexes (`wiki/domains/general/index.md`) — multi-level index already present.

**What is missing:**
- Structured frontmatter (`entities:`, `concepts:`) on source pages for deterministic edge traversal.
- Auto-generated index files with one-line descriptions (current domain indexes are bare wikilink lists, no descriptions).
- Concept/entity pages as first-class pages with `description:` fields.

## Proposed Design: LLM-Guided Traversal Loop

### Core idea

Replace `_load_wiki_context` with a loop where the LLM is shown only index content first and asks for the next page to read. The traversal logic (reading a file, following a wikilink) is deterministic Python. The LLM provides only the _next path_ as output.

### Loop contract

```
INPUT  to LLM each step:
  - The question
  - Pages already read (path + content)
  - A list of available next paths (from the current page's wikilinks + unvisited index entries)

OUTPUT from LLM each step (structured, e.g. JSON):
  {
    "action": "read" | "answer",
    "path": "<wiki-relative path>"   // only when action == "read"
  }
```

When `action == "answer"`, the loop exits and the LLM generates the final answer from accumulated context. This keeps the LLM out of the traversal mechanics entirely — it cannot invent paths, only select from the list provided.

### Pseudocode

```python
def navigate_and_answer_v2(question, history, wiki_dir, chat_fn, max_steps=8):
    visited = []
    context_pages = []

    # Step 1: always start from the root index
    root_index = (wiki_dir / "index.md").read_text()
    available = _extract_wikilinks(root_index)   # deterministic from [[...]] links
    context_pages.append(("index", root_index))
    yield _sse({"type": "status", "message": "Reading index…"})

    for step in range(max_steps):
        next_action = _ask_next_step(question, context_pages, available, chat_fn)

        if next_action["action"] == "answer" or not available:
            break

        path = next_action["path"]
        if path in visited:
            break
        visited.append(path)

        page_content = (wiki_dir / f"{path}.md").read_text()
        context_pages.append((path, page_content))
        available = _extract_wikilinks(page_content) - set(visited)
        yield _sse({"type": "status", "message": f"Reading {path}…"})

    # Final answer pass — same as today, but with traversal-collected context
    context = "\n\n".join(f"=== {p} ===\n{c}" for p, c in context_pages)
    return _answer_from_context(question, history, context, chat_fn)
```

### Navigation prompt (the `_ask_next_step` call)

```
You are navigating a wiki to answer: "<question>"

Pages read so far:
<path>: <first 200 chars of each page>

Available next pages (extracted from wikilinks):
- <path1>
- <path2>
...

Reply with exactly one JSON object:
{"action": "read", "path": "<one of the available paths>"}
or
{"action": "answer"}

Choose "answer" only when you have enough context to fully answer the question.
```

The available list is built deterministically from `[[wikilinks]]` extracted by `extract_wikilinks` (`scripts/core/wiki_graph.py:9`) — the LLM cannot hallucinate paths.

### SSE event changes

No new event types needed. The existing `status` event carries each traversal step:

```python
yield _sse({"type": "status", "message": "Reading index…"})
yield _sse({"type": "status", "message": "Reading domains/general/index…"})
yield _sse({"type": "status", "message": "Reading concepts/graphrag-documentation…"})
```

The frontend already renders these as italic navigation log lines (`chat/page.tsx:151–158`).

One optional addition: a `navigate` event type for richer UI (showing which node was visited in the graph view):

```typescript
type SseEvent = ... | { type: "navigate"; path: string; depth: number }
```

This is optional and does not affect the answer quality.

## Ingestion Changes Required

To make traversal work well, source pages need richer frontmatter so index files can be auto-generated with descriptions. Three targeted changes:

### 1. Add `entities` and `concepts` frontmatter to source synthesis

In `scripts/core/synthesize.py`, extend `_SOURCE_SYSTEM` to emit:

```yaml
entities:
  - "[[<slug>]]"     # bare-term wikilinks
concepts:
  - "[[<slug>]]"
```

These are already extractable from prose wikilinks (`extract_wikilinks` in `wiki_graph.py`); they just need to be promoted to frontmatter so a future `count_mentions.py`-equivalent can count them without re-parsing prose.

### 2. Add `description` to domain/concept pages

The `_TERM_SYSTEM` prompt in `synthesize.py:45–64` already writes concept pages. Add a `description` field to the frontmatter template (one sentence). This lets index files show a one-line summary per page — matching the reference's index format — so the LLM can decide which page to read without fetching each one.

### 3. Auto-generate index files

Write a script (equivalent to `scripts/build_index_md.py` in the reference) that walks `wiki/` frontmatter and regenerates each `index.md` with `title — description` bullets. This replaces hand-written indexes and is the primary enabler of progressive disclosure: the LLM sees descriptions at layer 1 and only fetches pages that look relevant.

## Rollout Sequence

1. **Add `description` to concept/entity synthesis** (synthesize.py) — zero breaking changes, backward compatible.
2. **Build `scripts/core/build_index.py`** — regenerate domain and root indexes from frontmatter.
3. **Implement `navigate_and_answer_v2`** in `chat_service.py` behind a feature flag (`WIKI_NAV=graph` env var).
4. **Re-ingest existing sources** to populate `description` and `entities`/`concepts` frontmatter.
5. **Remove old `_load_wiki_context`** once v2 is validated.

## Open Questions

- **Local model capability.** `llama3.2:3b` (`_OLLAMA_MODEL` default in `chat.py:24`) may not reliably produce `{"action": "read", "path": "..."}` JSON on every step. The navigation prompt may need a constrained output format or a retry loop.
- **Max steps vs. context budget.** Each traversal step adds a full page to context. With `llama3.2:3b`'s 128k context window this is not a hard limit, but latency grows linearly. A sensible default is 5–8 steps.
- **Graph view integration.** The graph page (`apps/web/app/graph/page.tsx`) already renders nodes. Emitting `navigate` SSE events would let the graph view highlight the traversal path in real time — a compelling UX, but deferred.
- **Write-back (questions/notes).** The reference's Q.5 write-back makes the wiki self-improving. This is architecturally sound but requires write access from the chat path, which is currently read-only. Worth a separate ADR.
